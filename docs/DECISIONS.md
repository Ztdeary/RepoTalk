# 关键技术决策

每个决策按「背景 → 备选 → 选择 → 代价 → 验证」记录。数字均来自 `docs/EVALUATION.md` 的 30 题消融实验，可复现。

---

## 1. 按 AST 函数/类切分，而不是按字符窗口切分

**背景**
代码问答需要回答「这个函数/类在哪个文件、第几行、做什么」。固定字符窗口会把函数拦腰截断，检索到的片段既不能编译也不能定位，LLM 只能猜。

**备选**
- 固定窗口（512 / 1024 字符）滑动切分：实现最简单，但必然切碎函数
- 整文件入库：上下文完整，但单块过大，向量被稀释，且无法给出精确行号
- 按行窗口 + 重叠：能保证覆盖，仍会切碎语义单元

**选择**
tree-sitter 解析后以函数/类节点为边界切块，写入 `file_path` / `start_line` / `end_line` / `symbol` 四个元数据；模块级零散节点合并为一块；超长函数不切、标记 `(large)`；无 parser 的语言降级到关键字切分。

**代价**
- 切分依赖语言 parser，新增语言要补 grammar
- 超大函数（数千行）会撑上下文，只能靠后续截断
- 跨函数的调用链信息拿不到，只能靠检索命中单个定义

**验证**
- 检索命中后能直接给出可引用的文件与行号（前端引用可定位）
- 混合检索 Recall@6 = 95.0%、MRR = 0.967；纯向量只有 3.3%，说明"块的质量"已经不足以救向量检索，真正起作用的是元数据 + 词法召回

## 2. 多路召回 + RRF 融合 + rerank，而不是只换 embedding 模型

**背景**
最初只有向量检索，实测在代码定位题上几乎全错（Recall@6 = 3.3%）。中文短 query 与英文大函数块在 bge-m3 空间里距离很远，top-6 大量落在 `utils.py`/`exceptions.py` 的通用代码上。

**备选**
- 换更强的 embedding / 更大的向量模型：成本高，且"中文问句 vs 英文代码"的语义鸿沟不是换模型能解决的
- 只做 BM25：词法命中好，但同义词、注释语义、改写提问会漏
- 向量 + BM25 分数加权融合：两路分数量纲不可比（余弦距离 vs BM25 分），权重要按数据集调，脆弱

**选择**
向量（top-80）+ BM25（top-80）+ 符号精确匹配（`filter={"symbol": ident}`）+ 逐字原文召回 + 界面元素召回 → 自写 RRF（只看名次，规避量纲）→ 标识符精确加分 → 同 (文件, 符号) 最多保留 3 条、候选上限 30 → bge-reranker 精排 → 精确命中的定义块兜底置顶 → 取 top-6。

**代价**
- 单题检索从 0.21s 涨到 2.20s（多路 DB 查询 + 外部 rerank）
- 符号召回依赖"从 query 抽标识符 + 停用词表"这类启发式，换语言要重新验证
- rerank 是外部 API，失败时必须降级为 RRF 顺序（已实现）

**验证**
| 模式 | Recall@6 | MRR@6 | 单题耗时 |
|---|---|---|---|
| 纯向量 | 0.033 | 0.017 | 0.21s |
| 混合 + RRF | 0.950 | 0.967 | 1.22s |
| 再加 rerank | 0.983 | 0.983 | 2.20s |

rerank 只值最后 3.3pp，但把定义块从第 2 名提到第 1 名、降低下游上下文噪声，所以保留；如果延迟成为硬约束，可以只对 `usage`/`class_location` 类问题开 rerank。

## 3. SSE 流式 + 检索期心跳 + 成本闸门

**背景**
一次完整问答要 2–10 秒（检索 + rerank + 生成）。同步返回时用户以为页面卡死；Nginx/中间代理会掐掉长时间无数据的连接。

**备选**
- 轮询任务 ID：要额外维护任务状态和清理逻辑
- WebSocket：双向能力用不上，代理与鉴权配置更复杂
- 一次性返回：实现最省事，体验最差

**选择**
- `POST /chat/stream` 用 SSE：先推 `status: retrieving`，再推 `sources`，最后逐 token 推 `token`，以 `done`/`error` 收尾
- 检索丢进 `asyncio.Task`，主循环在等待期间发 `: ping` 注释帧，防止代理因空闲断连；LLM 阶段 token 持续流动，不需要心跳
- 检索结果按 `repo_id + question` 缓存到 Redis，重复问题跳过整个检索阶段
- 成本闸门：演示模式只喂 4 块上下文、输出上限 320 token；访客每日提问/提交仓库配额；BYOK 走访问卷白名单
- rerank 失败自动降级为 RRF 顺序，不让整条链路失败

**代价**
- 前端要写 SSE 解析与半途失败处理，后端要维护生成器状态
- Nginx 三项配置不能动：`proxy_buffering off`、`proxy_http_version 1.1`、`proxy_read_timeout 300s`
- 已知缺陷：客户端断连后生成器不会立刻停止，LLM 仍会多消耗一段 token（已列入后续修复）

**验证**
- 首个 `status` 帧在检索开始前发出，用户立即有反馈
- 长检索期间心跳保活，公网 Nginx 下流式进度不中断
- 同问题二次提问跳过检索（Redis 命中）
